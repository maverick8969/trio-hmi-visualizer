# Trio Simulator

A software-in-the-loop simulator for Trio Motion controllers, built into the HMI visualizer. It
**executes your actual TrioBASIC `.BAS` programs** against a simulated controller and plant, so you can
test and troubleshoot logic, sequencing, interlocks, control loops and safety behavior **before
flashing any firmware**, and drive it all from your **real operator HMI**.

This repo bundles only a small synthetic project, `samples/demo/`, so the tools work out of the box.
Point them at your own controller project to simulate a real machine.

## Running it

It's a self-contained browser app (HTML/JS/CSS, no build step, no dependencies) and runs the same on
**Windows, macOS, or Linux** in any modern browser (Chrome, Edge, Firefox, Safari).

Serve it over a tiny local web server, then click **◉ Simulator** in the toolbar:

- **macOS / Linux:** `./start.sh` (or `python3 -m http.server 8000`) → open `http://localhost:8000`.
- **Windows:** double-click `start.bat` (or run `python -m http.server 8000`) → open `http://localhost:8000`.

The local server is only needed so the simulator can fetch the bundled demo and its Live-HMI screens.
Browsers block those fetches when you open the page directly as a `file://` URL. You *can* still open
`index.html` directly; then load your project with **Load .BAS…** (and the HMI with **Load Folder**).

To simulate your own machine, use **Load .BAS…** and pick the project's `.BAS` files plus its
`.mpv3prj` (for the autorun program) and, optionally, its `sim/scenarios.json`.

Headless (no browser), for CI and agents:

```bash
node tools/trio-sim.js --bas path/to/controller-repo --fast-boot --dump globals
node tools/hmi-shot.js --bas path/to/controller-repo --hmi path/to/hmi --out shots
```

## The demo project

`samples/demo/` is a made-up cell, not a real machine: START/STOP/RESET, a speed setpoint the actual
speed ramps to, a part counter with batch stop, hold-to-run jog and homing, and a drive fault.

| File | Purpose |
|---|---|
| `DEMO_MAIN.BAS` | autorun: declares the globals (`cmd_word` = VR 10, `status_word` = VR 11, …), sets defaults, starts the other programs |
| `CELL_LOGIC.BAS`, `JOG_LOGIC.BAS` | the cell's scan loops |
| `manifest.json` | autorun program and file list for the browser loader |
| `sim/scenarios.json` | the demo's regression scenarios |
| `hmi/` | operator screens (TGM + TGDs) generated by the `trio-hmi-screens` skill; `VR_MAP.md` lists the VRs |

## What it does

The simulator boots your project like the controller does: the autorun program runs, declares its
globals and launches the other programs. It runs the **real code** on a cooperative multi-process
scheduler that mirrors the Trio scan model (1 ms base tick, per-process `TICKS`, `WA()` sleeps,
`WAIT UNTIL` polling).

Because the engine is backed by the visualizer's live `vrStore`, your **real HMI screens** animate in
real time while the code runs, and operator writes from the HMI flow straight back into the running
program (see **Interactive HMI** below).

The engine covers the TrioBASIC language subset the parser recognises (`IF`/`WHILE`/`REPEAT`/`FOR`/
`GOTO`/`GOSUB`, `GLOBAL`/`CONSTANT`/`DIM`/`LOCAL`, `RUN`/`STOP`/`PROC_STATUS`, `WDOG`, `WA`, bit
operations, `TABLE`, `USER_PID`), servo axes with `FORWARD`/`REVERSE`/`CANCEL`/`MOVEABS`/`DATUM` and
`SPEED`/`ACCEL`/`DECEL` ramps, digital and analog I/O, EtherCAT and Modbus stubs with fault injection,
and an E-stop / watchdog / STO model.

### Plant physics (simple & tunable)

`js/sim/trio-plant.js` holds first-order models: servo motors ramp to commanded `SPEED` via
`ACCEL`/`DECEL` (point moves use a trapezoidal profile that stops on target); heater zones warm toward
a ceiling when energized and cool toward ambient when off; pump mass-flow tracks `MSPEED`; a nip-roll
drive and a mixer VFD are modeled as analog/PDO drives. The heater, pump, nip and mixer models are wired
to a specific pumping/mixing line's I/O; with other projects they simply stay idle. Rate constants
(`heatRateCPerSec`, `coolK`, `flowGperSecPerRPM`, `ambientC`, …) are illustrative, **not** calibrated.

## Interactive HMI

Click **🖥 Live HMI** in the simulator bar. This loads the operator screens (the demo's `hmi/` by
default) and switches to the HMI view with the engine running.

It is a true closed loop on your code: clicking an HMI button writes a VR → the running Trio program
reads it → the system responds → the code's outputs write VRs → the HMI animates. A floating **SIM**
control bar (bottom-right) lets you run/pause, change speed, and jump back to the engineering dashboard
while you interact with the screen. The VR panel on the right shows every bound register updating live.

## Using the dashboard

- **Transport** — `Boot`, `Run`/`Pause`, `Step 100 ms`, `Fast-boot` (run the boot instantly), speed 1×–100×.
- **Operator Controls / Motors & VFDs / Production** — panels for the plant models above; they write
  and read the same VRs the HMI buttons drive.
- **Fault Injection** — press/release E-stop, pulse the safety-relay reset, drop EtherCAT, or kill meter comms.
- **Processes / Axes / Heaters / Flow** — live state: each process's current line and run/sleep state, axis `MTYPE`/`MSPEED`/`MPOS`, zone temperatures, pump rpm/flow.
- **Regression Scenarios** — the loaded project's scenarios with pass/fail assertions (see below).
- **Digital & Analog I/O** — `OP`/`IN`/`AOUT`/`DV_IN`; click an input to force it.
- **VR Watch** / **Event Log** — filter and watch any named global; every `RUN`/`STOP`, `PRINT`, and warning (undefined identifier, unimplemented command, …).

## Regression scenarios

Each project keeps its own scenarios in **`sim/scenarios.json`** (an array of `{ name, steps }`).
`trio-sim --scenario all` and the dashboard's **Regression Scenarios** card run them; nothing
machine-specific is built in. Steps boot, drive inputs, inject faults, advance time, and assert:

```json
{ "name": "START latches RUNNING and ramps speed", "steps": [
  { "boot": true }, { "run": 1000 },
  { "setBit": { "name": "cmd_word", "bit": 0, "value": 1 } }, { "run": 3000 },
  { "expect": { "what": "bit:11.0", "op": "=", "value": 1 } },
  { "expect": { "what": "speed_actual", "op": "~", "value": 50, "tol": 1 } }
]}
```

Other steps: `{ "fastforward": ms }`, `{ "set": { "name": value } }` (`"VR:123"` for a raw VR),
`{ "estop": true }`, `{ "fault": { "name": "ethercatDrop", "on": true } }`. `what` supports `wdog`,
`VR:24`, `bit:24.0`, `axis:1:MSPEED`, `op:20`, `temp:<zone>`, `flow:<pump>`, `nip:running`,
`mixer:rpm`, or any global name; `op` is `=`, `!=`, `>`, `<`, `>=`, `<=`, or `~` (approx within `tol`).

> **Interpreter note:** TrioBASIC `AND`/`OR` are bitwise (they agree with logical for 0/1 operands).
> The engine implements them bitwise and `NOT` logically. Engine language behavior is covered by `tests/`.

## Architecture

```
js/sim/
  trio-lexer.js       tokenizer (comments, _ continuation, $hex, TIME$ suffix, context-aware .bit)
  trio-parser.js      recursive-descent AST (permissive: unknown commands never break parsing)
  trio-runtime.js     AST -> flat instruction list; multi-process scheduler; symbol table
                      (GLOBAL aliases -> VR, CONSTANT, DIM arrays); WDOG/TICKS/WA; RUN/STOP/
                      PROC_STATUS; USER_PID
  trio-machine.js     VR table, servo axes + ramp/trapezoidal physics, VFD/analog axes, digital+
                      analog I/O, home switch, EtherCAT/Modbus/CoE stubs
  trio-plant.js       tunable thermal + flow models, nip drive + mixer VFD models
  sim-controller.js   browser orchestration: build engine, load programs + HMI, rAF loop, boot/reset
  sim-scenarios.js    declarative scenario/assertion runner
  sim-ui.js / sim.css dashboard, Motors panel, operator controls, faults, scenarios, live-HMI wiring
samples/demo/         synthetic demo project (programs, scenarios, HMI)
```

**Design choices:** the parser is permissive (recognised keywords parse into structured nodes;
everything else becomes a generic assign/command the runtime interprets), and the AST is lowered to a
flat instruction list so cooperative multitasking is a simple instruction-pointer advance — a
`GOTO label` loop yields one scan per slice while `FOR`/`WHILE`/`REPEAT` run to completion within a
scan. The machine is backed by the visualizer's `vrStore` (change-detecting) so the running code and
the HMI share one VR table.

## Testing

`npm test` runs every `tests/test-*.js` in its own Node process.

- Always run: `test-demo` (the demo parses and passes its scenarios), `test-cli` (the headless CLI on
  the demo), `test-parser`, `test-fixes`.
- Line 2 tests (`test-scenarios`, `test-pid`, `test-traverse`, `test-drives`, `test-recipes`,
  `test-share`, `test-cli-line2`, `test-scenario-harness`) exercise the engine against the Line 2
  controller project, whose code is not stored here. Set `TRIO_LINE2_DIR` to a checkout of the Line 2
  repo to run them; otherwise they report SKIP:

  ```bash
  TRIO_LINE2_DIR=../line2 npm test
  ```
